# 予備ECU 診断プロトコル調査結果

対象: 予備ECU（Denso 279700-4073 / Mazda LFG7 18 881D, SH7058）
CAN 500kbps / 要求 0x7E0 / 応答 0x7E8 / ISO-TP 通常アドレッシング・8バイトパディング

## 識別情報（OBD-II Mode 09）

- VIN(09 02): `NCEC103017`
- CALID(09 04): `LFG7EG000LFN60A0`
- CVN(09 06): `74 ec 05 dd`

## バス上の自発送信フレーム（内部CAN、受動観測）

0x200, 0x201, 0x215, 0x231, 0x240, 0x420, 0x4EC, 0x4F0, 0x4F1, 0x4FF が周期送信されている。
（ECU単体でも送信。車両ネットワーク上の各ユニット宛のデータと思われる。将来解析。）

## 対応している診断サービス

| SID | サブ | 結果 |
|---|---|---|
| 01 | 各PID | OBD-II Mode01 対応（supported: 00/20/40 で応答あり）|
| 03 / 07 | — | DTC 読み出し対応（現状 stored=`01 c1 21`）|
| 09 | 02/04/06 | VIN/CALID/CVN 対応 |
| 22 | 16bit DID | ReadDataByIdentifier 対応。番号体系は Mode01 と共通（22 00XX）。全域スキャン結果は logs/ |
| 3E | 01 | TesterPresent は **3E 01 のみ**（3E 00 / 3E 80 は NRC 0x12）|
| 10 | 81/85/87 | StartDiagnosticSession（KWP2000形式）。10 02/03（UDS）は非対応 |
| 27 | 01 | SecurityAccess requestSeed 対応。**3バイトシード** |
| 23 | — | ReadMemoryByAddress は存在するが未認証では NRC 0x22（conditionsNotCorrect）|

## セキュリティアクセス（27）

- セッション `10 85` または `10 87` に入ってから `27 01` でシード取得。
- シードは3バイト（例: 85→`37 ff fb`、87→`b8 a9 14`）。レベルは 0x01 のみ（03/05… は NRC 0x31）。
- キーは3バイトを `27 02 kk kk kk` で返す形式と推定。
- **未検証**: キー計算アルゴリズム。公開情報（RomRaider / Mazda コミュニティ等）で確認してから、
  ユーザー確認の上で1回ずつ送る。間違えると試行回数カウンタが進みロックアウトの恐れ。

## 既存オープンソースツール（NC Miata 専用）

- **cdufresne81/nc-flash**（および fork: rusefi, LukaChassaing, yiraeryu）: J2534/UDS で読み書き。
  Python。CAN/UDS 層・セッション・チェックサム・フラッシュ手順が参考になる。
  - **ただしシードキー計算アルゴリズム本体は非公開**（`src/ecu/_secure/_security.py` は private。
    公開リポジトリには `_secure_stub.py` のみ＝全 fork 同じ）。
  - constants.py から得た有用な定数:
    - ROM 1MB、CAL_ID オフセット `0xC0046` / `0xB8046`、ROM_ID `0xFFC4C`
    - チェックサム: magic `0x5AA5A55A`、テーブル `0xFF650`–`0xFF7FC`、12バイト/エントリ（4バイトBE×3）
    - フラッシュ回数カウンタ: `0xFFB00`（8バイト、ROM書き込みごとにECUが刻む。読み戻し照合では除外）
    - SBL: サイズ `0x1800`、アップロード先 `0x8000`。ダウンロード領域 `0x8000`〜（サイズ `0xFF800`）、ブロック `0x400`
    - 電圧ゲート: 12.0V 未満はフラッシュ拒否
- **speepsio/romdrop**: ROM 定義（RomRaider 形式 XML）の集まり。
  - **我々の CALID に対応する `lfg7eg.xml` を取得済み** → `defs/lfg7eg.xml`（879テーブル、内部ID `LFG7EG` @ `0xB8046`）。
    将来のマップエディタの定義として直接使える。

## シードキー・アルゴリズムの判明事項（本体は未入手）

- 方式: **LFSR**、3バイトシード → 3バイトキー（nc-flash のテストコードより）。
- 検証用の既知ペア（実機キャプチャ由来）:
  - `B3 A8 4A` → `44 70 E8`
  - `AA C1 02` → `7F 26 F4`
- これら2ペアと「24bit LFSR」前提で、実機に触れずオフラインで復元を試行中（lfsr_solve2.py）。
  - no-const で厳密一致が出れば誤検出確率は極小（≈数e-6）＝ほぼ正解と判断できる。
  - 実機へキーを送る（`27 02`）のは誤キーでロックアウトの恐れ → **送信前にユーザー確認**。

## ROM 解析（ncec_rom_dump.bin, 1MB, CALID LFG7EG000.HEX, SH-2E big-endian）

実機の 0x27 は**毎回ランダムなシード**を返す（例: 5d17c6, 3f7350, c0c4be…）→ キーはシードから計算される方式。

- SH-2E 逆アセンブラ（tools/shdis.py, capstone）とエミュレータ（tools/sh2emu.py）を自作。
- **固定キーのダミー系統**: 標準ディスパッチャ 0x1488 → 0x27 ハンドラ 0x17F0 は固定シード `55 AA 55`・固定キー `4D AC CD`。これは実機のランダム挙動と不一致＝実際に使われる系統ではない。
- **実セキュリティハンドラ**: 0x7A7F4（r5=サブ機能）。
  - requestSeed はランダムシードを生成し、グローバル **0xFFFF91AD-AF** に保存。応答は共通ビルダ 0x7A99E（`mov #0x67`）経由、送信関数は **0x8D8C8**。
  - セッション/セキュリティ状態のゲートはグローバル **0xFFFF91A7 / 0xFFFF91A8**（0 だと NRC 0x31/エラー。実機で `10 85/87` を先に要求したのと一致）。
  - キーはおそらく sendKey 時にシードから計算して比較。計算本体は 0x7Dxx 群（0x7DD46/0x7DDEE=seed生成, 0x7DE0C=3byte比較, 0x44DC=memcpy, 0x3920/0x3934=割り込み制御）。
- **重要な判明**: nc-flash の既知ペア（B3A84A→4470E8 等）は、本ROMをエミュレートしても再現しない。
  → このECUのキー計算は**ECU固有値を含む可能性が高く、既知ペアでは検証できない**。
  → したがって「本ROMを丸ごとエミュレートして、実機が返したシードに対する正しいキーを算出する」方式が最も確実（推測なし）。

## ★ セキュリティアルゴリズム 解決済み

キー計算の本体は ROM の **`0x7DFE0`**（sendKey から呼ばれる検証関数）。
- 入力: シード3バイト(ポインタ r5) + 受信キー(r6) + レベル index(r4=1)
- 固定素材: **`"MazdA"`（4D 61 7A 64 41, @0x83BAC）** をシードの後ろに連結 + レベルテーブル(@0x83BB1)
- 64ラウンドのビット処理で期待キーを生成し、受信キーと3バイト比較（一致で r0=0 → 肯定、不一致で NRC 0x35）。

`ncecu/security.py` の `compute_security_key(seed, level=1)` が、ROM内 0x7DFE0 を SH-2E
エミュレータ(`ncecu/sh2emu.py`)で実行して正しいキーを算出する。**推測なし（実ROMロジックそのもの）。**

検証（いずれもロックアウトのリスクなしで実施）:
- 公開既知ペア 2 組を完全再現: B3A84A→4470E8, AAC102→7F26F4（index=1）。
- 自己整合テスト 25/25: ROM自身の検証関数が、算出キーを全件受理し、誤キーを全件拒否。

実機ドライラン（送信なし）: `10 85` → seed `7c 39 c9` → 算出 key `38 11 36`。
→ 残るは実機へ `27 02 <key>` を送る最終確認のみ。

## 次の計画

1. エミュレータでセッション状態ゲート（0xFFFF91A7/A8）を満たし、requestSeed→sendKey を完走させる。
2. 「保存シード→期待キー」を算出する部分を分離し、実機が返す任意のシードに対して正しいキーを計算できるようにする。
3. エミュレータ内で自己整合（算出キーを sendKey に入れて受理されること）を確認。
4. **実機へ送信（27 02）する前にユーザー確認**（誤キーはロックアウトの恐れ。ただしエミュレータ算出なので誤りの主因はエミュレータのバグのみ）。

## ダンプ(ncec_rom_dump.bin)と実機の一致検証

直接メモリ読み出し(0x23)は実機で全アドレス NRC 0x31 のため、1バイト単位の実機比較は不可（SBL方式が必要）。
代わりに以下で検証:

1. **アンロック成功が最強の証拠**: ダンプ内の鍵ルーチン(0x7DFE0)と定数("MazdA"等)で算出したキーを
   実機が受理(67 02)。アルゴリズム/定数に1バイトでも差があれば鍵は不一致になるため、
   **少なくともセキュリティ領域はダンプ＝実機でバイト一致**が確定。
2. **CALID 部品一致**: 実機 Mode09 CALID「LFG7EG000LFN60A0」の構成要素
   「LFG7EG000」(@0xB8049付近) と「LFN60A0」(@0xB8061) がダンプ内に存在。
3. **内部チェックサム全35領域が検証OK**: チェックサムテーブル(0xFF650)の各 (開始,終了,格納値) で
   `32bitワード和 + 格納値 = 0x5AA5A55A` が全件成立 → **ダンプは完全・無破損の正規ROM**。

→ 総合すると、**ダンプはこの実機のキャリブレーションと一致していると高い確度で言える**。
   ただし全バイト厳密一致の最終証明にはしていない。
   CVN(実機 09 06 = `74 ec 05 dd`)の再現検証:
   - ROM全体を検索 → 74EC05DD はどのバイト順でも**格納されていない** = 実行時計算値。
   - CRC32テーブルなし。領域チェックサム(35領域)の 和/XOR/部分和、累積ワード和/バイト和(各種補数・
     マジック関係)いずれも不一致 → **OBDコード内の独自ハッシュ**。
   - Mode09データ供給の追跡: 0x8B960系ハンドラ→データビルダ→供給関数 0x8BCE8/0x8BD1A は
     ROMテーブル 0x84CB0 を引くのみ(CVN無し)。CVNハッシュ算出ルーチンは別途未特定。
   - 厳密なCVN一致検証には Mode09 ハンドラの本格エミュレーション(鍵解読と同手法)が必要=相応の工数。
   - 追加調査: Mode09 ハンドラ エントリ = 0x8B930、PIDは RAM 0xFFFF9A5F から読む、送信関数 0x8D8C8、
     サポートPIDビットマップ 0x54000000 @0x84DB0 (=PID 2/4/6対応)。
   - prefix-sum で全区間を調べたが、CVN=ワード和となる「整列境界の領域」は存在せず → CVNは混合ハッシュで確定。
   - サービスディスパッチテーブル発見: 0x84B48 開始、12バイト/エントリ (service_id, handler_ptr, flag)。
     0x09→Mode09ハンドラ 0x8B930、0x27→セキュリティ 0x7A7F4 等。
   - **CVN算出ルーチンを特定: `0x8BC90`**。Mode09ハンドラ 0x8B9C4 で `cmp/eq #6`(PID==06)が成立すると
     0x8B9CA `bsr 0x8BC90` で呼ばれる。
   - 0x8BC90 をエミュレートしようとしたが、プロローグ直後(0x8BC98)に **FPU系の未対応命令(0xFFFB)** が出現し停止。
     → CVNは浮動小数点を使う計算の可能性。完全再現には sh2emu.py に **FPU命令の実装追加**が必要（未完）。
   - sh2emu.py に **SH-2E FPU を実装済み**(FADD/FSUB/FMUL/FDIV/FMOV/FTRC/FLOAT/FLDI 等)。
   - 0x8BC90 は FPU 実装後に完走(38ステップ, ret=0)したが CVN は出ず。内訳を追うと、
     0x8BC90 → [0x85286]/[0x8529E] → **0x1B978 / 0x1B984(RTOSのタスク間メッセージング、RAM構造体 0xFFFF6Cxx 操作)**。
   - 結論: **CVNは起動時にバックグラウンドタスクが計算してRAMにキャッシュし、Mode09はそれを取得するだけ**。
     単一ルーチンのエミュレーションでは再現不可。再現にはECUのRTOS全体の駆動が必要=非現実的。
   - **→ CVNによる定量検証は実務上断念。** 一方、直接メモリ読み出しサービスも無い(0x35非対応, 0x23ゲート)ため、
     バイト厳密比較の手段は（現アクセス範囲では）存在しない。
   - 一致判定は既存の3根拠(アンロック成功/CALID一致/内部チェックサム全35領域正当)で**高確度**が最終結論。

## フラッシュ書き込み(0x34/0x36/0x37)解析

サービスはメインディスパッチテーブル(0x84B48〜)に登録、flag=0x06=プログラミングセッション+セキュリティ要:
- 0x31 RoutineControl → 0x7C048
- 0x34 RequestDownload → 0x7F610  (検証後、RTOSタスクへメッセージ送信 [0x7a038])
- 0x36 TransferData → 0x7F688
- 0x37 TransferExit → 0x7F6C8
実処理はバックグラウンドのRTOSタスク側(CVN同様)。外部プロトコルは確定済み。

**確定したフラッシュ手順(このECU固有・KWP2000系, nc-flash解析+本ROM逆アセンブルで確認):**
1. 10 85 プログラミングセッション
2. 27 01/02 セキュリティ(解読済み)
3. 22 E6 11 フラッシュ回数(識別)確認
4. **34 <addr:4BE> <size:4BE>** RequestDownload(フォーマットバイト無し。既定 addr=0x00008000, size=0x000FF800)
5. **36 <生データ>** TransferData(0x400バイト毎、シーケンス番号なし)
   - ① **SBL を RAM 0x8000 へ転送** → ② **ROMプログラムデータ(rom[flash_start:]) を転送**
6. 37 TransferExit
7. 11 01 ECUリセット
書き込み前にチェックサム補正が必須(ncecu/checksum.recalculate)。

ホスト側ドライバ実装済み: **ncecu/flash.py**(ドライラン検証済み。SBL+confirm無しでは書き込まない安全設計)。

**唯一の欠落 = SBL(セカンダリブートローダ, 0x1800バイト)**:
RAM 0x8000 に転送され、受信したプログラムデータをオンチップ・フラッシュ・プログラミングで書き込むRAM常駐カーネル。
nc-flash は SBL を非公開(host-only IP, flash_start/世代でパラメタ化)。→ 入手不可。
自前で SBL を書く必要がある(SH7058 の ch24 オンチッププログラミング仕様を使用。相応の組込み開発+ブリックのリスク)。

### 安全検証の結果(実機, 書き込みなし)

- 10 85 / 27(アンロック 67 02)/ 22 E6 11 / B1 00 B2 00 すべて動作確認。
- 22 E6 11 応答 = "SW-LFG7EG000.HEX"(実機のSW IDがダンプ 0xB8046 と一致 → ダンプ=実機の再々確認)。
- **RequestDownload `34 00008000 000FF800` は NRC 0x10 (generalReject)** で拒否(22 E6 11 を先に実行しても同じ)。
  nc-flash と同一バイト・同一順序でも拒否 → ECU は追加の前提条件を要求(RTOSフラッシュタスク側の状態要件と推定、未特定)。
  J2534(Tactrix)と gs_usb の差の可能性もあるが、ISO-TPは成立(正規のNRCが返るため)。
- 0x34 が拒否されたので消去・書き込みは発生していない(安全)。
- 残課題: (1) 0x34 を受理させる前提条件の特定(RTOSタスク解析)、(2) SBL の自作。両方とも大きめ。

### ★ A 解決: RequestDownload の前提条件 = RoutineControl `B1 00 B2 00`

nc-flash の check_flash_counter は `22 E6 11` ではなく **`B1 00 B2 00`**(RoutineControl 0xB1, routine 0x00B2)。
正しい順序: `10 85` → `27`(アンロック) → **`B1 00 B2 00`** → `34 <addr><size>`。
実機で確認: 0x34 が **`74 04 01` で受理**(以前 generalReject だったのは B1 00 B2 00 を抜かしていたため)。
データ未転送でリセット → 消去・書き込みなし(安全)。ncecu/flash.py の check_flash_counter を B1 00 B2 00 に修正済み。
(注: 0x34ハンドラ自体はエミュレーションで [91A8] に関係なく常にダウンロードメッセージを投函 → 拒否はRTOSタスク側で、
B1 00 B2 00 未実行が原因だった。)

## B(SBL)調査結果 — ROM逆解析

- **ECUユーザーROMにフラッシュ制御レジスタ(0xFFFFE8xx/A8xx/C8xx)へのアクセスは皆無**。
  `mov #0xA5` はROM全体で1箇所のみ=0x10F10のCPU自己テスト(FKEY書き込みではない)。
  → **フラッシュ書き込みコードはECUに常駐せず、アップロードするSBL内にのみ存在**(SH7058のチップ内蔵
    ルーチンをRAMへダウンロードする方式)。nc-flashがSBLを必須かつ非公開にする理由。
- 0x34(0x7F610)も 0x36(0x7F688)も、検証後は**同じ 0x79F8A でRTOSフラッシュタスクへメッセージ投函**するだけ。
  SBLの実行ハンドオフ・データ処理・受け渡しABIは**すべてRTOSタスク内**=CVNと同じ静的解析困難な壁。

### Bの実現性評価(正直な見積もり)

SBL完成には以下が必要で、いずれも重い:
1. RTOSフラッシュタスクの解析で「ECU→SBLの受け渡しABI」を特定(CVN同様、静的には極めて困難)。
2. SH7058のフラッシュ・プログラミングSBLを自作(チップ内蔵ダウンロード方式。無印SH7058の正確な仕様が必要。
   手持ちは SH7058S マニュアルで、方式は同系統の可能性が高いが未確認)。
3. 実機テスト(ブリックの実リスク)。
→ 事実上の組込みファーム開発で、オープンソース界が唯一非公開にしている部分。A(前提条件)は解決済みだが、
  Bは別次元の規模。
