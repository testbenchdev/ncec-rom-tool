# 自前書き込みの実現性と設計(option 2 — SBLを待たずに書き込む)

対象: 予備ECU(Denso 279700-4073 / Mazda LFG7 / Renesas SH7058)。
前提: **スペアのみ・ブリック許容**。現物ECUには触れない。
調査日: 2026-10-03。出典: SH7058 F-ZTAT ハードウェアマニュアル Rev.3.00 第23章
(`docs/sh7058_plain_manual.pdf`)、nc-flash / mx5studio / LibreTuner のソース。

---

## 結論(先に要点)

書き込みを「自前で」実現する経路は2つあり、**片方は実質不可、もう片方は現実的**。

| 経路 | 方式 | 判定 |
|---|---|---|
| **2a** | CAN プログラミングセッション + 自作SBL(ユーザプログラムモード) | ✕ **不可** — ハンドオフABIがRTOSタスク内で静的RE不能 |
| **2b** | **SH7058 ブートモード(SCIシリアル)** | ◎ **現実的** — 書き込みアルゴリズムはチップ内蔵、自作SBL不要 |

**推奨 = 2b(ブートモード)。** 理由:
- 書き込み/消去ルーチンは**チップ内蔵のブートプログラム**が実行 → 非公開SBLもRTOS解析も不要。
- ホスト側は**シリアルでコマンドを送るだけ**(Pythonで実装可能)。
- **原理的にブリック不能**: ブートモードはハードピンで起動する回復モード。書き込み失敗しても再進入して再書き込みできる(CAN/SBL方式は失敗=永久ブリックの危険があるが、こちらは安全)。
- コスト = **基板上のSH7058ブート関連ピンへの物理アクセス**(唯一の障壁)。

---

## 2a が不可な理由(確認済み)

- フラッシュ書き込みコードは**ユーザROMに常駐しない**(FLMCRアクセス皆無を逆解析で確認)。
- CANの `0x34/0x36` ハンドラは検証後 RTOSタスクへメッセージ送出(`0x79F8A → 0x8E4FA → 0x8e534`=システムコール・トランポリン表)。
- アップロードしたRAMコード(0x8000)への制御移譲は**ダウンロード先変数経由でRTOSタスク内**にあり、`jmp/jsr @Rn` の特定は静的解析では不能(CVN再現と同じ壁)。2026-10-03に再確認。
- nc-flash等はこの経路をSBL込みで実装しているが、**SBLは全ツールで非公開**(nc-flashの`_secure`はhost-only、公開は例外を投げるスタブのみ)。

→ 2a で書くには結局SBL入手(= option 1)が必要。自前では詰む。

## 2b: SH7058 ブートモード(推奨)

### モードピン設定(表23.1)
| ピン | ブートモード |
|---|---|
| RES | 1(リセット解除後) |
| **FWE** | **1** |
| **MD2** | **1** |
| **MD1** | **0** |
| MD0 | 0/1(0=外部バス可 / 1=シングルチップ) |

通常のユーザモードは MD2=1/MD1=1。**ブートは MD1=0 にする**のが要点。基板がMD1を固定している場合はピンリフト/トレースカット+プルダウンが必要。FWEは多くのECUで書き込み用に端子/ジャンパが出ている。

### 物理接続
- **SCI1**: `RxD1`(ECU受信), `TxD1`(ECU送信)。USB-シリアル変換(3.3Vロジック, 8bit/1stop/パリティ無)。
- リセット線(ブートモードピン確定後にリセットを掛ける)。
- 電源。

### ブートストラップ(ビットレート自動調整, 図23.27)
1. ホスト → `H'00` を最大30回連送
2. ブート → `H'E6`(ブート応答)、低レベル期間を測定
3. ブート → `H'00`(調整完了)
4. ホスト → `H'55`
(ホストのビットレートは **9600 または 19200 bps**、システムクロック20〜40MHz)

### コマンド方式(§23.9, 表23.18)
フレーム形式: `コマンド(1) [サイズ(1-2)] [データ] チェックサム(1)`。チェックサムはコマンド〜SUMの総和が`H'00`になる値。応答は通常「コマンド+0x10」(例 `H'20→H'30`)、ACKは `H'06`、エラーは `H'9x + エラーコード`。

照会・選択コマンド:
| コード | 名称 |
|---|---|
| H'20 | Supported Device Inquiry(→H'30) |
| H'10 | Device Selection(→H'06) |
| H'21 | Clock Mode Inquiry(→H'31) |
| H'11 | Clock Mode Selection(→H'06) |
| H'22 | Multiplication Ratio Inquiry(→H'32) |
| H'23 | Operating Clock Frequency Inquiry(→H'33) |
| H'24 | User Boot MAT Information Inquiry(→H'34) |
| H'25 | User MAT Information Inquiry(→H'35) |
| H'26 | Block for Erasing Information Inquiry(→H'36) |
| H'27 | Programming Unit Inquiry(→H'37) |
| H'3F | New Bit Rate Selection |
| H'40 | **Transition to Programming/Erasing**(全MAT自動消去して書込状態へ) |
| H'4F | Boot Program Status Inquiry |

必須の選択順: `H'10(デバイス) → H'11(クロックモード) → H'3F(ビットレート)`。

書き込み/消去(§23.9 続き、標準F-ZTATコード。実装前にマニュアルpp.911-920で最終確認):
- プログラミング選択(ユーザMAT)→ `開始アドレス(4) + データ(=プログラミング単位=128) + SUM` を単位ごとに送信、終了は開始アドレス `H'FFFFFFFF`。
- 消去選択 → ブロック番号、終了は `H'FF`。
- その他: Sum Check / Blank Check / Memory Read / Status。

### 重要な性質
- `H'40` で **ユーザMAT + ユーザブートMAT を全自動消去** → **1MB全体を書き戻す**必要がある(我々は完全ダンプを保有。チェックサムは`ncecu.checksum`で補正済み)。
- ユーザブートMAT(別MAT)は通常運用では未使用の見込み。消去されたままでも通常ブートには影響しないはずだが、要確認。
- 書込は**128バイト単位**、各ブロックは**消去後1回のみ**書込可(再書込厳禁=破損)。

## 実装ロードマップ(2b)

**Phase A — ホスト側ソフト(ECU不要で作成可能)**
- `tools/bootmode_flash.py`(新規): pyserial で auto-baud → デバイス/クロック/ビットレート選択 → `H'40` → 128バイト単位で全ROM書込 → ベリファイ(Sum/Blank/Read)。
- プロトコルのユニットテスト(フレーム生成/チェックサム/応答解釈)をモックで。
- 既存資産を流用: 完全ダンプ、`ncecu.checksum`(補正)、ブロック構成(EB0-15)。

**Phase B — ハードウェア(ユーザ作業)**
- ECUを開け、SH7058(256QFP)の `FWE / MD0 / MD1 / MD2 / RES / RxD1 / TxD1` を特定。
- ブートモード用ハーネス作成(モードピン確定+SCI+USBシリアル3.3V)。
- MD1をboot側(0)へ、FWEをHighへ。

**Phase C — ベンチ試験**
- ブートモード進入 → auto-baud 応答(`H'E6`/`H'00`)確認 → 各Inquiryでデバイス/MAT/ブロック情報取得 → 全消去 → 全書込 → ベリファイ → 通常モードへ戻して起動確認。
- 失敗しても**ブートモード再進入で復旧**(un-brickable)。

---

## 低コストの合流点(option 1 と重なる)
- **誰かの実機フラッシュのCANログ**が手に入れば、`0x36` 転送の先頭ブロック群が **SBLバイナリそのもの**(平文)。これを `ncecu/flash.py`(検証済みドライバ)に渡せば、2bのハードウェア作業なしに CAN 経由で書ける。
- つまり「SBL入手(1)」と「ブートモード自作(2b)」は独立に進められる。1が先に入手できれば2bのハード作業は不要。

## Phase B 調査結果(2026-10-03)— ハードウェアアクセスと物理リスク

出典: Nissan/Denso ECU RE Wiki(SH705x Bootmode)+ NC Miata コミュニティ。NCのECUは
Denso SH7058 なので、Subaru/Nissan と同じ Denso ブートモード手法が適用できる。

### ★ 朗報: 破壊的な基板加工は不要(必要信号はテストパッドに出ている)
NC(および同系 Denso)ECU の**基板裏に6点×2群のテストパッド**があり、ブートに必要な信号が
そこに出ている:
- 電源群: **VBat / GND / +5V**
- 制御群: **WDT / MD1 / SCI1_TX / SCI1_RX / nRES**

→ **QFPピンのリフトもトレースカットも不要**。細線をパッドにはんだ付けするだけ。
(user mode は MD1=1、boot は MD1=0 なので、MD1 を GND に落とすだけで切替可。MD0/MD2 は
boot と user で共通のため触らなくてよい見込み。)

### ブートモード・リグ手順(Denso SH705x)
1. **nRES を ≤22Ω 経由で GND**、**MD1 を ≤22Ω 経由で GND**。
2. 電源投入と同時に **WDT パルス列を供給**(外部スーパーバイザICがMCUをリセットし続けるのを防ぐ。
   正常時の **PL5 の波形を測定して模倣**、約125Hz)。← これが無いとCPUが延々リセット。
3. **nRES を解放**(安定を確認)。
4. シリアル **19200 8N1**: `0x00` を最大30回連送 → `0x55` → `0xE6`(boot OK)受信。
5. 以降、§23.9 のコマンド方式(本書 2b 節)。

### 物理リスク評価(懸念への回答)
- **破壊的操作(ピンリフト/トレースカット)は不要** → 最悪の基板破損要因は回避できる。
- 残る物理リスクと対策:
  - **パッド剥がれ**(配線に引張/せん断がかかると剥離)→ ストレインリリーフ必須、線を引っ張らない。
  - **誤配線/過電圧** → SCIは3.3Vロジック、投入前に全結線をテスタ確認。
  - **WDTパルス・リグの用意**(555 or マイコンで波形生成)= 手間だが基板破損要因ではない。
  - **FWE の扱い**: 上記パッド群に明記が無い。基板側で処理/固定の可能性。実機で要確認
    (FWE=1 が無いと消去/書込は実行されない)。
- 総合: **物理リスクは「低〜中」で管理可能**。必要なのは精密はんだ付けの技能のみ。
  フラッシュ面は**ブートモード=回復モードなので再進入で必ず復旧(un-brickable)**。
- **ただし**: 物理リスクを完全にゼロにしたいなら、**option 1(CAN経由=OBDコネクタのみ・基板非接触)が最安全**。
  2b は「1が入手できない場合の自立手段」と位置づけ、物理作業は納得できるまで着手しないのが妥当。

### 要確認(実機・ただし今はソフト/偵察のみ)
- この個体(279700-4073 / PCB 279721-3521)基板での**テストポイントの信号対応**。
- **FWE** の結線、**MD0/MD2** の既定状態、**WDT 波形**(周波数/デューティ)。

### この個体の基板で確認できたこと(表面写真, 2026-10-03)
- MCU = 右上の金属枠付き大型4方向QFP(= SH7058。表面は研磨で型番判読不可)。主水晶 **10.0MHz**。
- **ブートアクセス候補(いずれも未実装スルーホール=はんだ不要でプローブ/ピン挿し可)**:
  1. **基板右端のティアドロップ型テストポイント列(約20点)** — 各点からトレースが扇状に伸びる
     = Denso工場テスト点。MD1/nRES/SCI1/WDT/FWE はこの中にある可能性が高い。
  2. **「G709 E」2列ヘッダ**(右下、未実装スルーホール2列)。
- ※表面写真だけでは**各点の信号を確定できない**。確定には下記のいずれか。

### ブートモード・リグの具体(RomRaider/Tactrix/Nissan-wiki で標準化)
- 必要信号(テスト点): **WDT, MD1, SCI1_TX(TxD1), SCI1_RX(RxD1), nRES** + **GND, +5V/VBat**。
- シリアル: **FTDIのTTL TXD/RXD** を直結(SCI1)。**555タイマ**でWDTパルスを生成しCPUリセットを防ぐ。
- 起動: nRES と MD1 を **≤22Ω経由でGND** → 電源投入+WDTパルス → nRES解放(2〜3秒5V安定を確認)。
- **注意**: nRESは基板でVccへプルアップ済み&オープンドレインで引かれ得る。**nResをVcc直結は厳禁**
  (GNDへ≤22Ωで引くだけ)。
- ホストソフト: **EcuFlash の "Flash Recovery Mode"(File→Options→Flashing)が SHブートモードで書く**
  → 自作 `bootmode_flash.py` が無くても既存ツールで可能。RomRaider系の手順書・回路図あり。

### ★ SH7058(FP-256H)確定ピン番号 — 公式マニュアル図1.2より目視確認(2026-10-03)
INDEX(ピン1)は図の左下。**下辺=ピン1〜64**、右辺65〜128、上辺129〜204、左辺205〜256。
ブートに必要なピンは**下辺の10MHz水晶のすぐ隣に集中**している:

| ピン | 信号 | 用途(ブート) |
|---|---|---|
| 50 | **MD2** | boot=1(=user mode と同じ。触らない) |
| 51 | EXTAL | 10MHz水晶の片脚(位置の基準) |
| 53 | XTAL | 10MHz水晶の片脚(位置の基準) |
| 55 | **MD1** | **boot=0 → ≤22ΩでGNDへ**(user mode は1) |
| 56 | **FWE** | 消去/書込に **High(=1)** が必要 |
| 57 | HSTBY | ハードスタンバイ(通常Highのまま) |
| 58 | **RES**(反転) | **≤22ΩでGNDへ→解放**(Vcc直結厳禁) |
| 59 | **MD0** | 0/1(user mode のまま。触らない) |
| 165 | **PC0/TxD1** | SCI1 TX(ECU→ホスト)。FTDIのRXへ |
| 166 | **PC1/RxD1** | SCI1 RX(ホスト→ECU)。FTDIのTXへ |

(間の 49=Vcc, 52=Vcc, 54=Vss, 48=CK。GNDは Vss 多数。)

**位置特定のコツ(ピン1を数えなくてよい)**: 基板の **10MHz水晶**を見つけ、その2脚をたどると
MCUの **EXTAL(51)/XTAL(53)**。そのすぐ隣が **50=MD2**、水晶の反対側へ順に
**54,55(MD1),56(FWE),57,58(RES),59(MD0)**。→ 水晶を基準に数本数えるだけで全部特定できる。

**WDT について**: WDTパルスは MCU の WDTOVF ピンではなく、「MCU→外部スーパーバイザIC」の
ウォッチドッグ・サービス線(基板依存のGPIO)。**ECUを通常起動させた状態でテスト点を当たり、
約125Hzで振れている点がWDTノード**。ブート時はそこへ555等で同等パルスを注入する。

### 信号対応を確定する方法(物理リスク別)
- **リスク0**: (a) **miata.net DIYスレッド**(NC固有のパッド図。※ご自身のブラウザで開けます/当方はbot対策で不可)、
  (b) **基板裏写真**(後日)、(c) **テスターで導通確認**(各テスト点↔SH7058の該当ピン。はんだ不要)。
- 低リスク: 確定後、スルーホールに**ピンヘッダ/ポゴピン**で接触(細パッドへのはんだ付け回避)。

### 低リスクの偵察ステップ(はんだ付け前)
基板裏写真 or miata.netのNCパッド図が得られれば、上記候補のどれが各信号かを割り出せる
(配線・はんだ付け不要=物理リスクゼロ)。その上で着手可否を判断すればよい。
