# ノック補正まわりの徹底RE（「ノック値が変化しない」の検証）

提出ログでノック系の値が一度も変化しない、という指摘を受けて、純正ノック制御を読み取り専用でREし、
全ログと突き合わせた（2026-11-14、ベンチECUの吸い出し原本 `rom_data/ecu_readout_yahooauction.bin`。実車ROMも同CAL `LFG7EG` で該当コード一致）。

## 結論（確定版）

**ノック制御は正常に動いており、ログにも実際に3回、ノック遅角が記録されていた。**
「変化しない」ように見えたのは、ライブ表示の番地とラベルが3つ間違っていたため。

| 旧ラベル | 番地 | 本当の意味 | 「変化しない」の正体 |
|---|---|---|---|
| ノックリタード（候補） | `0xFFFF7C44` | **本物のKR（ノック遅角）** | 動いていた（3回、各1.7°・約0.25秒）。短いので見落としやすい |
| ノックカウント | `0xFFFF7C3A` | **始動後の燃焼回数（255で飽和）** | 走行中は常に255が正常。ノック回数ではない |
| KR（ノック遅角） | `0xFFFF7C4C` | 表 `0xBBDF0`「KR積算に必要な最小KR」の引き値 | KRではないので 3.9〜4.6° で動くだけ |
| ノック強度 | `0xFFFF7C60` | 未確認の別項（ノック強度ではない） | アイドル付近で 15.0 が一瞬出るだけ |

全開ログで KR=0 だったのは、**その場面でノックセンサのレベルがしきい値を超えなかった＝ノック未検出**、が正しい読み。

> 同日の途中説明は2つとも誤りだったので破棄する。
> ①「低負荷でリスン窓外だから0」→ 全開でも0だったので不成立。
> ②「上流イネーブル `0xFFFF4E14` が非活性」→ `0xFFFF4E14` はイネーブルではなく検出フラグそのものだった（下記）。
> なお②の「大半のセッションで0だった」は実測ではなく推測だった（`0xFFFF4E14` を読んだログは無い）。

## 信号の流れ（コードで確認）

```
ノックセンサ → 気筒ごとの窓で取り込み → ノックレベル 0xFFFF4E20
                                              │  ≥ 適応しきい値 0xFFFF4E58 ?
                                              ▼
                              生検出 0xFFFF4E14 ──写し──▶ 0xFFFF7E89
                                                              │ かつ 始動後燃焼数 0xFFFF7C3A ≥ 24
                                                              ▼
                                              ノックイベント 0xFFFF7C3C
                                                              ▼
                                  KR 0xFFFF7C20（+1.7°、上限8°、のち減衰）──写し──▶ 0xFFFF7C44
```

- **生検出 `0xFFFF4E14`**（書き手は 0xB100 の初期化と 0xB61A–0xB62C のみ）。クランク角イベント 0xB21C →
  気筒別処理 0xB32A の末尾で、`しきい値 0xFFFF4E58 > レベル 0xFFFF4E20` なら 0、そうでなければ 1。
  - レベル `0xFFFF4E20`：取り込み値（`0xFFFF4E74`−オフセット `0xFFFF4E16`）×5/65536 → 表 `0x93028` で換算
    → ゲイン段と気筒別補正を加減（0xB33C–0xB3A2）。
  - しきい値 `0xFFFF4E58`：`平均 0xFFFF4E3C + ノイズ 0xFFFF4E54 × 倍率 0xFFFF4E18` を
    下限 `0xFFFF7E74`／上限 `0xFFFF7E70` でクランプ（0xB51C–0xB5F2）。倍率の初期値は 3.25（`0xB8320`）。
  - この判定は気筒イベントごとに走る。読んだ範囲では回転・負荷で止める条件はこの層に無い
    （窓の開閉 0xB658 / 0xB780 は取り込みタイミングの設定で、全部は読んでいない）。
    回転・負荷の条件（Knock Listen：1000〜5250rpm かつ 負荷40%以上）は、この後の KR 側で効く。
    **5250rpm を超える領域は cal 上そもそもノック判定の対象外。**
- **写し `0xFFFF7E89`**：0x52A40 で `7E89 = (4E14 != 0)`。それだけ。
- **始動後燃焼数 `0xFFFF7C3A`**：0x4FE06。状態バイト `0xFFFF7346` の bit7（初期化で 0x80。ログでは停止中に立っている）が
  立っていれば 0、そうでなければ飽和加算（0x2478、上限255）で +1。初期化時（0x4F80C）にも 0。
- **ノックイベント `0xFFFF7C3C`**：0x4FDDC–0x4FE02。`7E89==1` かつ `7C3A ≥ 24`（uint8 `0xBBCA7`）で 1。
  ＝始動直後の24燃焼ぶんは検出を無視するだけの条件。
- **KR**：本体は `0xFFFF7C20`（0x4FDCC でリセット、0x4FCB8 で読まれる）。`0xFFFF7C44` はルーチン 0x4FCAC の最後
  （0x4FD54）で書かれる1イベント遅れの写し。表示用にはどちらでも同じ。
- **`0xFFFF7C4C`**：0x4FF2E–0x4FF3C で表 `0xBBDF0`（`KR Accumulator - Minimum KR for Accumulation`＝
  5.625 / 4.57 / 3.867 / 3.16 / 2.8…）を引いた値。0x4FD18 で「KRがこれ以上なら積算（学習）する」の比較に使う。

## ログでの裏付け

### `0xFFFF7C3A` は始動後の燃焼回数
冷間始動から記録した `logs/livelog_20261105_211638.jsonl`（ECT 21℃、t=0 で 0rpm）：

| t[s] | rpm | 0xFFFF7C3A |
|---|---|---|
| 0.00 | 0 | 0 |
| 2.52 | 852 | 1 |
| 2.60 | 1402 | 5 |
| 2.85 | 2090 | 22 |
| 3.50 | 1332 | 57 |
| 4.00 | 1233 | 78 |
| 7.97 | 990 | 204 |
| 以後 | — | 255 固定 |

増え方は約43回/秒（1300rpm＝1回転に2燃焼）。他のログは始動後に接続しているので最初から255。
`..230145` も稼働時間3〜8秒＝始動直後だったので255未満が写っただけ。**255固定は正常。**

### `0xFFFF7C44` は本物のKR（全ログで3回作動）
| ログ | t[s] | rpm | 負荷 | ECT | KRの動き |
|---|---|---|---|---|---|
| `..20261105_211638` | 10.39 | 1198 | 66% | 21℃ | 0 → **1.70** → 1.36 → 1.19 → 1.02 → 0.68 → 0.34 → 0 |
| 同上 | 282.66 | 1127 | 62% | 66℃ | 0 → 1.53 → 1.19 → 1.02 → 0.68 → 0.51 → 0.17 → 0 |
| `..20261102_182622` | 62.02 | 1327 | 52% | 77℃ | 0 → **1.70**（約0.9秒保持）→ 0.6455 → 0.294 → 0 |

- 立ち上がり 1.70 ＝ `Knock Detected - KR Increment Rate`（1.7、`0xBBCAC`）。
- 0.17 刻みの減衰 ＝ `KR Decrement Rate | Knock Listen Active`（0.17、`0xBBF98`）。
- 3件目は負荷が40%を割った瞬間から 0.3515 刻み（1.7 − 3×0.3515 = 0.6455）＝
  `KR Decrement Rate | Knock Listen Inactive`（0.3515、`0xBC0FC`）。`Knock Listen - Minimum Load` は 0.4（`0xBBD88`）。
- 1・2件目は同じタイミングで点火時期（PID 0x0E）も1〜2°落ちている（3件目は回転上昇で進角中のため判別しにくい）。
- 3件とも **1100〜1330rpm・負荷52〜67%**（低回転で踏んだ場面）。全開の場面では出ていない。

3件目の「約0.9秒保持」は減衰開始の待ち（`Timing Restoration - KR Reduction Delay`）と思われるが、未確認。

## 是正（適用済み）

- **ノック監視は「レベル＋KR」の2本に集約**（ユーザー指示「レベルとKRで十分」）。`ncecu/livelog.py` 既定 と `ram_reads.json`：
  - **追加** `0xFFFF4E20`（ch 0x114, f32, role `KNOCKLVL`）＝ノックレベル。センサの強さの連続値。
  - `0xFFFF7C44`（ch 0x106）を **role `KR`「KR(ノック遅角)」** に。読み出し 0.2秒。
  - **撤去**（意味は本書に残す。必要なら `ram_reads.json` で追加）：
    ノックイベント `0xFFFF7C3C`（ch 0x10E）／生検出 `0xFFFF7E89`（ch 0x10F）＝KRがあれば冗長。
    始動後燃焼カウント `0xFFFF7C3A`（ch 0x104, すぐ255飽和）／`0xFFFF7C60`（ch 0x105, 未確認）／
    旧「KR」`0xFFFF7C4C`（ch 0x102, KR積算の最小KRの引き値でKRではない）。
    途中で足した `0xFFFF4E14`（ch 0x110）は `7E89` と同値なので削除。
  - チャンネル番号と番地の対応は変えていない（過去ログはそのまま読める）。
- `ncec_dashboard.py`：ラベルをレベル(0x114)＋KR(0x106)に。**警報を修正**：「カウント≥24で赤」（走行中ずっと赤になる誤り）と
  「0x102≤−3で赤」（KRではない）を撤去し、**KR(0x106) ≥ 1.5° で赤**に。レベルは内部スケールのため既定レンジ0〜5（実車で調整）。
- `ncec_chart.py`：既定で表示するノック系列を 0x102 → レベル0x114＋KR0x106 に。
- `docs/live_ramread_ja.md` の該当表・説明・設定例を差し替え。

## まだ分かっていないこと（正直な範囲）

- **「全開で本当にノックしていないのか」までは静的REでは言えない。** 言えるのは、検出の連鎖は生きていて
  （低回転で3回作動）、全開の場面ではレベルがしきい値を超えなかった、というところまで。
  余裕度を見るには `0xFFFF4E20`（レベル）と `0xFFFF4E58`（しきい値）を `ram_reads.json` に足して全開を1本記録する。
  どちらも f32。気筒イベントごとに更新される値を数十ms間隔で拾うので、傾向を見る用途。
- `0xFFFF7C60` の正体（アイドル付近のアクセル踏み始めで 15.0 が約0.15秒出る）。
- KR積算（学習）側 `0xFFFF7C30` の挙動。ログの3件は KR が「積算の最小KR」（3.9°前後）に届いていないので、
  積算は一度も起きていないはず。

## RE上の注意（ツール）

- ノックCALは `0x000BBxxx` 帯なので、ROMの4バイト一致走査はジャンプ表（`rts;bsr`＝`000b b___`）と偽陽性で衝突する。
  実 `mov.l @(disp,PC)` のロードだけを拾うこと。
- FPU命令は capstone(SH2) で復号できない。FPU対応の簡易逆アセンブラ（scratch の `shfpu.py`）を使った。
- **番地の意味はコードだけで決めず、ログの値が cal の定数と一致するかで確かめる**（今回 KR を確定できた決め手）。
